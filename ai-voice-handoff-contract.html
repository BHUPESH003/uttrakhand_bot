Overview

Same escape hatch, one more input/output modality

This is an additive extension to ai-handoff-contract.html (v1.0), not a new integration. Once a user is inside Chat with us, they'll now be able to send a voice note instead of typing, and your service can reply with a spoken audio message instead of (or alongside) text. Everything about the lifecycle, conversationId, reserved sys:* control IDs, and the 3-block-per-turn cap from v1.0 still applies unchanged — this document only covers what's new: the audio message shape, and the new audio response block.

i

Scope of this document: how a voice note gets from the user to your API, and how a spoken reply gets back to the user. No bot code changes are in flight against this yet — same as v1.0, treat field names as proposed.

The bot never runs speech-to-text or text-to-speech itself — same principle as v1.0: it's a thin, deterministic relay. We fetch bytes off Meta because your service has no way to reach Meta's authenticated, short-lived media URLs directly.

Flow

Conversation lifecycle

Voice notes are just another shape of "the next message" inside an already-open AI_CHAT session — there's no separate entry point or menu row for voice.

1
User is already in AI_CHAT

Same entry as v1.0 — they tapped Chat with us. Nothing new here; voice only matters once conversationId exists.

2
User records a voice note instead of typing

The bot downloads the audio bytes from Meta (they expire in ~5 minutes and require our own bearer token — your service can't fetch them), then sends one Request exactly like a text turn, except message.type is "audio" and the text field is replaced by the audio payload.

3
Bot renders the response

Same messages[] array as v1.0, with one addition: a new audio block type the bot plays back as a WhatsApp voice/audio message. You can mix it with a text block (e.g. a transcript) in the same turn, within the existing 3-block cap.

4
Loop, or hand back

Unchanged from v1.0 — control.action and the reserved sys:* control IDs work identically whether the turn that produced them was typed or spoken.

New / changed fields

FieldTypeNotes
message.typetext | button_reply | list_reply | audioreqv1.0's union gains "audio". Exactly one of text / audio is populated depending on type — never both.
message.audio.mimeTypestringreqWhat Meta gave us. In practice always audio/ogg; codecs=opus for an in-app voice note — see media limits for why we're restricting to voice notes only in this phase.
message.audio.durationSecintegeroptFrom Meta's metadata when present. Useful as a cheap pre-check before decoding.
message.audio.encoding"base64"reqFixed value for this phase. We inline the bytes rather than hosting them ourselves — see why.
message.audio.database64 stringreqThe raw voice note, downloaded by us from Meta's temporary media URL. Never persisted by us beyond the audit log's request row — treat it as PII/sensitive the same as any transcript of speech would be.
⚠

Why base64-in-body, not a URL: Meta's media URLs require our own bearer token and expire in minutes — we can't hand you a link you can fetch. We also don't run any object storage in this demo (nothing to host a re-shareable URL from), so inlining the bytes is the lowest-infra option for this phase. A signed-URL relay is a reasonable thing to revisit for production — see open questions.

The new block kind

audioA spoken reply, played inline as a WhatsApp voice/audio message. audioUrl must be a public HTTPS URL — Meta fetches it directly, same as image/document in v1.0.≤ 16 MB · see formats
!

Asymmetric on purpose: inbound audio travels as base64 (we already have the bytes, you have no storage of ours to fetch from); outbound audio travels as a URL (you already have to render/host the TTS file somewhere, and this reuses v1.0's image/document pattern exactly — no new upload code on our side).

Response-side recommendation, not a requirement

Pairing every audio block with a short text transcript (as in the example above) costs you nothing extra to generate and meaningfully helps: users in a noisy or public place, anyone who prefers reading, and our own audit log (which stores the JSON body, not decoded audio) all benefit. Not enforced by the bot, just strongly suggested.

Unchanged

Everything else is reused verbatim from v1.0

To avoid duplicating the whole document, here's exactly what carries over with zero changes — see ai-handoff-contract.html for the full detail on each.

  • conversationId lifecycle, minted once per "Chat with us" entry, never replayed as history by us.
  • Reserved sys:* control IDs (sys:main_menu, sys:apply, sys:track, sys:download, sys:end_chat) — work identically whether the turn that returned them was typed or spoken.
  • control.action (continue | return_to_menu | end_session).
  • The 3-message-block-per-turn cap — an audio block counts toward it like any other.
  • Text formatting rules (WhatsApp's five-symbol markdown subset) for any text block in a voice-triggered turn.
  • Auth (Authorization: Bearer), the demo-phase timeout budget, and the "never a raw error to the user" fallback behavior — though see reliability below for one voice-specific addition to the budget.

Operational

Auth, timeouts & errors

Auth, retry behavior, and the error-response shape are all unchanged from v1.0 — see that document's reliability section. One addition specific to voice:

  • Timeout budget: still 25 seconds per call for this phase, same as text — but a turn now includes ASR + model + TTS on your side, plus us downloading the source audio from Meta on ours. If 25s turns out too tight once ASR/TTS latency is real, that's the first thing worth revisiting (flagged in open questions, not decided yet).
  • Audit logging: the request row logged to MessageLog includes the base64 payload today (mirrors how the full request is logged for text) — flagged under compliance as something to revisit before production, since it means spoken audio briefly sits in our own database.

Guardrails

Compliance notes specific to voice

The v1.0 document's compliance section (24h session window, content/conduct rules, data minimization, audit trail) applies unchanged. Two things are specific to voice and worth calling out separately.

1. Voice carries more signal than text

⚠

A recording can carry accent, background context, or a second speaker's voice in a way a typed message never does. Your service's retention policy for raw audio bytes (versus just the transcript) needs its own sign-off under the DPDP Act, 2023 — separate from, and stricter than, whatever's already agreed for waId / profileName retention in v1.0.

2. The base64 payload is logged today

Same as noted under reliability: our current audit table logs the full request body, which for a voice turn means the recording briefly lives in our Postgres instance. This is worth a joint decision before any real user data flows through this — options include redacting message.audio.data from the logged row, or a short TTL on that column. Not blocking for a demo, but flagged explicitly here rather than left implicit.

Beyond the contract

UX recommendations

Always give a text escape hatch

Same principle as v1.0's automatic Back to Menu button: a user who got a voice reply should still be able to type instead of talking on their next turn — nothing about entering voice mode should feel one-way. This falls out naturally since voice notes and typed text are just two shapes of the same message field turn-to-turn.

Transcript-first for low confidence

When ASR confidence is low (garbled audio, background noise), prefer replying with a clarifying text question ("Did you mean...?") over guessing and answering the wrong question in a confident-sounding voice clip — a wrong spoken answer reads as more authoritative than a wrong typed one.

Show it's processing

Same as v1.0's typing-indicator note — worth pairing with the bot marking the voice note "read" immediately (already true today for every inbound message) so a multi-second ASR+TTS round trip doesn't feel broken.

Before this ships

Decided vs. still open

Decided

  • Scope limited to in-app voice notes (audio.voice: true) — no general audio-file uploads in this phase.
  • Inbound audio travels as base64 in the request body; outbound audio travels as a URL, reusing v1.0's image/document pattern.
  • 120-second duration cap on inbound voice notes, enforced with the same graceful-fallback pattern as any other AI-turn failure.
  • Reuses the v1.0 contract's conversationId, control IDs, and 3-block cap without modification.

Still open

  • Is the 25-second timeout budget realistic once ASR + LLM + TTS run in sequence on your side, or does voice need its own (longer) budget?
  • Should raw audio bytes be redacted from our audit log, or kept with a short retention TTL, before any real user data flows through this?
  • Is a signed-URL relay (bot re-hosts the inbound audio briefly instead of inlining base64) worth building before production, to avoid inflating request bodies for longer voice notes?
  • Should a transcript text block be required alongside every audio block, or left as a recommendation (current stance)?
