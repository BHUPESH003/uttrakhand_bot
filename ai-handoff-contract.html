Overview

One escape hatch into a real conversation

Today's bot is a fixed menu tree. We're adding one new row — Chat with us — that hands the conversation to an external AI service for free-form Q&A, and hands it back the moment the AI (or the user) is done. The bot never runs any AI itself: it's a thin, deterministic relay that renders whatever the AI service tells it to send, using message types WhatsApp already supports.

i

Scope of this document: the HTTP contract between our bot and your API, the WhatsApp/Meta rules that contract has to respect, and UX suggestions. No bot code changes yet — this is what we're aligning on before anything gets built.

Flow

Conversation lifecycle

What happens between the tap and the hand-back — this is the loop the contract below has to support on every turn.

1
User taps "Chat with us"

A new row on the main menu, alongside Apply / Track / Download / Help. The bot mints a conversationId and enters a new AI_CHAT flow state.

2
Every message routes to your API

While in AI_CHAT, each inbound text, button tap, or list tap becomes one Request — except our existing global commands ("hi" to restart, "language" to switch), which still short-circuit the AI, same as they do today for the rest of the bot.

3
Bot renders the response

The Response's messages[] get sent in order using our existing WhatsApp client (text, buttons, list, cta_url, image, or document) — no new message-sending code required on our side.

4
Loop, or hand back

control.action decides what happens next: stay in the AI flow, jump to a specific deterministic menu, or close out back to the main menu. See reserved control IDs.

Every kind maps 1:1 to a method our WhatsApp client already exposes — nothing new to build for sending, only for routing.

These limits are enforced server-side by Meta — exceeding any of them fails the entire message (error 131009), not just the offending field. Validate before returning, don't rely on us to catch it.

Modularity

Reserved control IDs

Any button or list-row id you return that starts with sys: is intercepted by the bot itself — it's how the AI hands control back into our deterministic menus without knowing anything about how they're built. Anything else is treated as your own custom ID and simply comes back to you verbatim as the next message.replyId.

IDHands off to
sys:main_menuMain menu (same as today's "Back to Main Menu")
sys:applyCertificate-type picker (Birth / Death / Domicile)
sys:trackTrack-status flow
sys:downloadDownload-certificate flow
sys:end_chatCloses AI_CHAT quietly, back to main menu

Use these instead of trying to re-implement "Apply" or "Track" yourselves — they route into the exact same code path a menu tap would.

Operational

Auth, timeouts & errors

Auth

Authorization: Bearer <shared-secret> on every request, over HTTPS only. Rotation process/cadence is decided internally on our side, not something we need from your team. Never log the token or the full request body (it carries waId — PII).

Timeout & retries

  • Bot waits 25 seconds per call (demo-phase value — no p95 latency requirement set yet). No response in time is treated as a failure.
  • Bot does not auto-retry a failed call — the user's next message naturally starts a fresh turn. Make your own processing idempotent per requestId in case you retry internally.
  • On any failure (timeout, 5xx, malformed body), the bot sends a graceful fallback message plus a sys:main_menu button — never a raw error to the user.

Error response

4xx / 5xx
{
  "error": {
    "code": "UPSTREAM_TIMEOUT",
    "message": "Model call exceeded 25s budget" // logged only, never shown to the user
  }
}

Throughput

Meta's per-business messaging tiers cap total messages sent per day/second, shared across every bot-sent message — the fixed menu and the AI flow draw from the same budget. Cap messages[] at 3 blocks per turn: enough for an answer plus a next-step prompt, without flooding a small screen or eating the cap unnecessarily.

Guardrails

Meta & WhatsApp rules this contract has to respect

The AI can be asked almost anything, including "why" and "how" questions that push at the edges of what's allowed. These are the rules that actually constrain what a response can look like or when it can be sent.

1. The 24-hour session window

!

Business-initiated free-form messages — including every message type in this contract — are only deliverable within 24 hours of the user's last inbound message. Outside that window, only a pre-approved message template can reach them.

That's exactly what whatsapp.withinSessionWindow tells you on every request. If it's false, whatever you return in messages[] cannot be delivered — the bot will not attempt it. Don't design a flow that assumes this is always true.

2. Hard formatting limits

ElementLimit
Reply buttons per message3 max
Reply button title20 characters
List rows, total across all sections10 max
List row title24 characters
List row description72 characters
List button text20 characters
cta_url header text60 characters
Text message body4096 characters (hard); keep it well under for readability

3. Content & conduct

  • Stay in scope. Responses should stay within this being a government citizen service — no marketing, no third-party promotion, no content outside certificate services.
  • Honor opt-outs. A user who has tapped "Opt Out" in the main flow must never be re-engaged by the AI either — the bot enforces this at the routing layer, but it's worth knowing why AI_CHAT is unreachable for such users.
  • Disclose it's automated. Best practice (and good instinct for a government service): the very first message on entering AI_CHAT should say plainly that this is an automated assistant — not on every turn, just the entry point.
  • Content check before sending. We're adding our own content-check layer on the bot side that reviews every AI response before it reaches the user — independent of whatever moderation your service does internally.
⚠

Known gap for this demo: there's no human-escalation path yet — see the response contract's note on control.action. Meta's guidance (and general good practice) expects a way to reach a person; this should be revisited before any production rollout, not left as a permanent gap.

4. Data minimization

⚠

This bot handles Aadhaar numbers, full addresses, and other sensitive certificate-form data. None of it belongs in this contract. context.applicant is intentionally limited to name and coarse application status — enough to answer "where's my application", never enough to reconstruct someone's form.

As a state government service, this also falls under India's DPDP Act, 2023 obligations — get legal sign-off on what your service retains from user.waId and profileName, and for how long, before this goes live.

5. Audit trail

Every outbound message the bot sends — menu-driven or AI-driven — is logged today in one audit table keyed by phone number, direction, and payload. AI-flow messages will be logged exactly the same way, so admin retains one unified trail regardless of which layer generated the content.

Guardrails

Formatting "how / what / why" answers

WhatsApp text isn't HTML or Markdown — it supports exactly five things. Answers should look like they belong to the same bot as the rest of the menu, not like a different product bolted on.

SyntaxRenders as
*text*bold
_text_italic
~text~strikethrough
```text```monospace
\nline break (no native bullet/numbered list, no headers, no tables)

Good vs. not-quite

✓ Do this 
*Domicile Certificate — how to apply*

1. Tap *Apply for Certificate*
2. Choose *Domicile Certificate*
3. Fill the form we send you
4. Get your reference number here

Takes 3–5 working days.
✕ Not this 
## How to Apply for a Domicile Certificate

- Go to the menu
- Click apply
- **Fill** the <form>

| Step | Action |
|------|--------|
| 1    | Menu   |

Headers, real bullets, HTML tags, and tables simply won't render — they'll show up as literal characters on the user's screen.

  • Lead with the direct answer in *bold* — WhatsApp users scan, they don't read top to bottom.
  • Number steps by typing 1. 2. 3. — there's no real list markup, so this is the convention the rest of the bot's copy already uses.
  • One idea per text block; split a long answer into 2 sequential blocks rather than one wall of text (still within the 3-block-per-turn cap).
  • Match user.language exactly — never mix English and Hindi in the same message.
  • Close a substantive answer with a buttons block offering the logical next step, instead of leaving the user to type free text again.

Beyond the contract

UX recommendations

Things worth deciding now, most of which we'd bake into the bot side rather than ask the AI to remember every time.

Guarantee the escape hatch ourselves

Rather than trusting every AI response to include a way out, the bot will append a Back to Menu button after each AI turn automatically (merged into your own buttons, up to the 3-button cap if you've already used one or two). One less compliance-critical thing for your team to remember on every response.

Nudge, don't just expire

If the user goes quiet mid-conversation, one gentle "Still there? Tap Main Menu anytime" after ~10 minutes reads better than the session just silently running out the 24-hour window.

Act on low confidence proactively

When confidence is low, the bot can surface "Did that answer your question? [Yes] [No]" itself, rather than waiting for a frustrated user to ask twice — worth revisiting once a human-escalation path exists to route the "No" to.

Show it's "thinking"

The bot already marks incoming messages read immediately; pairing that with WhatsApp's typing indicator while your API call is in flight keeps a 25-second wait from feeling broken.

Feed the admin dashboard

intent and confidence are worth surfacing on a lightweight "AI conversations" view for staff — it's the fastest way to spot a recurring question that should really be a menu option or an FAQ, not an AI call at all.

Fail in character

The fallback message on a timeout or error should read like the rest of the bot's own copy — plain, apologetic, and helpful — not like a raw system error message.
